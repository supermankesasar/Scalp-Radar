## Opportunity detection and entry timing — developer proposal (2026-11-26)
User requests moving directly to improving opportunity detection and entry timing, and asks the developer to proactively define technical criteria rather than requiring the user to choose indicators/weights. This is a **design proposal**, not an implemented or validated strategy.
- Source inspection on main: app.py promotion_candidates uses 5m freshness, latest quote and chase gate then score/turnover sorting; scan_job promotes rolling Top5; minute_research_loop records 1m research separately; signals.py REACHED denotes target attainment, not entry confirmation. Existing R08 setup tags and R09/R10 shadow rules should be reused, not counted as independent validations.
- Proposed modular stages: opportunity detection (activity anomaly), setup/direction classification (continuation, reversal, breakout), then entry readiness (fresh 1m price structure/response, current quote, anti-chase, liquidity/available spread, invalidation). Separate trigger time, actual decision time, readiness and outcome. WAIT is an internal state, not a new neutral dashboard category; keep existing frontend. Preserve all eligible candidates including rejected/missed events independently of Top5 visibility.
- Avoid new arbitrary weighted score or silently promoting negative/unvalidated minute rules. Reuse existing thresholds as versioned provisional controls, test setup-specific alternatives prospectively while operational development proceeds. Breadth/BTC context is not an unconditional directional veto. Spread and rolling correlation require verification/possibly additional feature work; missing inputs are unknown, not zero. Use measured coverage, latency, lead time, recall/precision on explicitly defined events, missed opportunities, MFE/MAE and cost-sensitive outcome comparisons for manual decision support only. No auto-trading benchmark.
- Needed user input: latest R10 overnight export if available (including logs), optional examples of late/missed/false signals; developer handles code, rule definitions and evaluation. Absence of new export does not block implementation work; cannot claim improvement before observations. R08 remains baseline until challenger evidence is reviewed; no code or formula changes in this proposal.
